# Replies for #1519 (sprite batching)

## Thread: "Atlas duplicates resident frame textures" (src/Renderer/SpriteBatch.js, page upload loop)

Yes, on this PR the atlas pages are a second copy of each drawn sprite file's frames. The copy is the same bytes as the frames (one byte per pixel for palette frames, four for RGBA), plus the unused space at the end of each shelf. It's made only for files an entity actually draws, and MemoryManager frees it with the file.

The frame textures stay because the unbatched path still uses them: `spriteBatching: false`, frames too big for a page, and anything drawn outside the entity pass. I haven't measured GPU memory in a crowded scene. The bench above measured draws and frame times only.

#1520 replaces these per-file pages with shared texture arrays of fixed size, which grow up to a hard limit, so the copy has a ceiling there. I've put the numbers on that PR.

## Thread: "Batch resources survive context-loss bookkeeping" (src/Renderer/SpriteBatch.js, `open`)

Right. A restored context keeps the same context object, so `_gl !== gl` never noticed. Fixed in 3a9aeefa:
- `Renderer.onContextRestored` now calls `SpriteBatch.contextRestored()`, which drops the program, VAO and instance buffer, so the next `open()` creates them again.
- A generation stamp makes each sprite file pack its atlas pages again on its next draw.
- A new test in `tests/renderer/SpriteBatch.test.js` restores the context with the same context object and checks that both are rebuilt and the sprite still draws. It fails without the fix.

Separately, on `master` a restore already leaves `SpriteRenderer`'s own program and quad buffer on the lost context. Nothing calls `SpriteRenderer.init` again with them cleared, so sprites don't come back on master either. I've left that alone because it's outside this PR. With the fix above, the batch doesn't add to that problem.
